# ComPick — фронтенд (прототип интерфейса)

React + TypeScript + Vite + Tailwind. Работает вместе с backend ComPick (FastAPI).

## Запуск (на Mac)

1. Backend (из папки `backend/`):

   ```bash
   python3 -m uvicorn app.main:app --port 8000
   ```

2. Фронтенд (из папки `frontend/`):

   ```bash
   npm install   # один раз
   npm run dev
   ```

3. Открыть http://localhost:3000

Запросы `/api` и `/health` проксируются на `localhost:8000` (см. `vite.config.ts`).

## Страницы (по макетам «ComPick — макет конфигуратора ПК.pdf»)

- `/` — лендинг: назначение + бюджет → «Собрать ПК»; пример сборки справа пересчитывается при смене назначения и движении ползунка бюджета
- `/pick` — подбор сборки: назначение, бюджет, приоритетные детали; карточка предложенной сборки, предупреждение о неактуальных ценах, состояние «сборка не нашлась»
- `/configurator` — «Моя сборка»: строки категорий (без корпуса) со статусами «Подходит / Не подходит / Не подтверждается», блок накопителей (несколько дисков: SSD M.2/SATA + HDD, «+ Добавить накопитель»), баннеры с причинами и подсказками глоссария, пустые строки «Не выбрано», итог по лучшим ценам, панель проверки (сокет, поддержка CPU платой, тип памяти, мощность БП), цены магазинов с пометкой «не актуально», список для заказа
- `/configurator/replace/:category` — замена детали: сводка сборки, требование (сокет/тип памяти), фильтр «Только подходящие / Все», бейджи совместимости каждого кандидата, дельта цены к сборке
- `/catalog` — каталог: категории сбоку (включая «Накопители»), фильтр по бренду, поиск, бейджи «Актуально / Не актуально / Цена не определена»
- `/catalog/:id` — карточка детали: характеристики + предложения магазинов (наличие, актуальность цены, кнопка «Перейти в магазин»)
- `/builds` — готовые сборки по назначениям (через живой подбор backend; у каждого назначения свой бюджет и своя цена)
- `/help` — глоссарий терминов с поиском
- `/help/data` — «О данных»: демо-срез, обновление цен (раз в месяц), «цена не определена»

## Решения по данным (26.11)

- Предел актуальности цены — 30 дней (обновление раз в месяц); ранее был 24 часа. Затронут NFR-04: формулировку нужно обновить в документах.
- Подбор целится в бюджет: рекомендуется самая близкая к бюджету снизу подтверждённо совместимая сборка, поэтому у разных назначений/бюджетов разные итоговые цены.
- Форм-фактор корпуса и длина видеокарты в первой версии не проверяются — из интерфейса убраны.
- Корпус исключён из сборок (решение 26.11): в каталоге остался, в подборе и конфигураторе не участвует.
- В сборке может быть несколько накопителей (совмещаются SSD и HDD): POST `/api/builds/{id}/components` добавляет накопитель, DELETE `/api/builds/{id}/storage/{component_id}` убирает конкретный диск.
- Приоритетная категория профиля (у «игр» — видеокарта, у «учёбы» — процессор и т.д.) учитывается в ранжировании: среди сборок, одинаково близких к бюджету, выбирается та, где приоритетная деталь дороже.

## Особенности прототипа

- Несовместимая деталь не сохраняется в сборке (так устроен backend): она показывается отклонённой строкой с причиной, а совместимость кандидатов на странице замены проверяется пробной установкой на одноразовой копии сборки.
- Идентификатор сборки хранится в `sessionStorage` — после перезапуска backend (данные в памяти) сборка пересоздаётся.
- Админ-панель из макетов (стр. 10–17) не реализована: в backend нет ни авторизации, ни CRUD-эндпоинтов — это отдельная задача после появления БД и API админки.
